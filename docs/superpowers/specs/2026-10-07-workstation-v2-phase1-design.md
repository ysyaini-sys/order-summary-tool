# 个人工作站 V2 第一阶段设计

## 目标

在不改变现有浏览器本地工作站计算与页面入口的前提下，建立可重复执行的原功能基线、回归门禁和增量模块边界，为后续 Profile / Projects 接入提供外围承载。

## 当前范围与边界

当前仓库实际包含：

- 订单汇总：抖音、视频号、快手，本地文件处理。
- 投放数据汇总：平台、日期范围、消耗、成交、订单、ROI、转化成本。
- 千川商品分析：商品/视频文件解析、去重、筛选、导出和质量提示。
- 现有 Node.js 测试与 GitHub Actions 测试入口。

当前仓库未发现可直接验证的云端运行、通知/推送、MCP、整点盯盘和十大消耗业务实现。因此第一阶段只建立这些能力的回归检查占位与风险记录，不伪造通过结果，也不引入新的外部服务依赖。

## 方案

### 1. 回归基线

新增一份人工检查清单和一份机器可读检查定义。机器可读检查只验证仓库可观测的契约：页面入口、核心脚本存在、测试命令、数据隔离、本地处理、错误提示、去重和导出安全性。人工清单记录需要真实文件或部署环境才能验证的项目：账户抓取完整性、十大消耗抓取、整点盯盘、通知、云端运行和 MCP。

### 2. 自动化门禁

保留现有 `node --test tests/*.test.js` 作为唯一基础命令；补充基线测试，确保六个重点区域在代码结构或测试覆盖缺失时失败。GitHub Actions 继续运行同一命令，不修改核心计算逻辑。

### 3. 兼容层

新增独立的 `workstation/` 只读基线模块，提供：

- `loadBaseline()`：读取固定的基线清单。
- `evaluateBaseline(root)`：检查文件、脚本、测试与文档契约，返回逐项结果，不执行网络请求、不读取用户数据。

该模块不被现有页面调用，因此不会改变运行时数据链路。

### 4. Profile / Projects 外围模块

新增 `profiles/README.md`、`projects/README.md` 和示例元数据文件，规定目录格式与隔离原则；第一阶段不将其接入订单、投放或千川计算。

## 回归重点

自动检查至少覆盖：

1. 订单汇总三个入口存在且快手密码只在订单页。
2. 投放汇总和千川分析保持独立页面与独立脚本。
3. 千川商品/视频分析的重复、`全部` 行、长 ID、缺失指标和零成本口径有测试。
4. 账户文件漏读必须能由数据检查结果暴露，不能静默当作完整成功。
5. 十大消耗输入缺失或读取失败必须产生明确失败项，不能生成伪造排名。
6. 导出内容保持转义安全且不包含外部脚本。
7. Profile / Projects 文件不改变现有页面依赖关系。

## 风险处理

未接入本仓库的能力不会标记为“已通过”。清单会区分 `pass`、`not-applicable-to-repo`、`manual-required` 和 `fail`。只要仓库内自动检查失败，第一阶段不算完成；人工项在真实运行环境验证前保持未完成状态。
